# Each non-comment line records something the gate found and we have not yet closed, so that CI is
# green on the tree as it stands and only a NEW gap fails. A baseline is a record of known debt, not
# a place debt goes to be forgotten -- so it is enforced as a SET, in BOTH directions:
#
#   * an entry that is no longer produced is STALE and FAILS the gate. When the missing migration is
#     written, or a verification learns to read columns, the finding disappears and the line here
#     must be deleted in the same change. A forgiveness list that only ever grows stops recording
#     anything.
#   * a finding that is not listed here FAILS the gate. That is the point.
#
# The anchor bounds the committed history the gate walks. It is a commit, never a count: a rolling
# N-commit window would silently drop an entry out of scope, at which point the line here would read
# as stale and be deleted while the defect was still shipping.

# The three erasure-certificate columns below are a KNOWN gap with a filed decision, not an accepted
# shape. The shipped 001 declares all three, so a FRESH install is correct; a database provisioned
# before they were added has the table without them and re-running 001 does not repair it.
#
# They are recorded here rather than migrated because the backfill is a compliance decision and not
# a schema edit. There is no payload blob to recover the values from -- these columns ARE the
# certificate -- and the row carries a Signature computed over the OLD field set, so populating them

# distinction here. The backfill semantics are an open decision, tracked internally.

# THE PRE-RC SCHEMA RESET -- one event, and the reason every entry below looks alike.
#
# Until this reset, each package shipped a create script plus a chain of in-place migrations, and
# this gate's question -- "does every in-place change to a create script ship an ALTER a consumer can
# follow?" -- was the right one to ask. It is not the right question before RC any more, and the
# change is deliberate rather than a lapse.
#
# The chain was removed from every package. Each now ships create scripts only, already at the final
# shape, and a schema change is delivered by EDITING THE CREATE SCRIPT so that a new consumer never
# inherits a sequence of edits that undo each other. The consequence is exactly what this gate
# detects: every historical in-place column change now has no ALTER behind it, because none is
# offered. A database provisioned by an earlier prerelease has no upgrade path and is re-provisioned.
#
# WHY THESE ARE LISTED RATHER THAN THE ANCHOR MOVED. Moving the anchor to the reset commit empties
# the gate's window, and this gate REFUSEs an empty population rather than passing it (its own
# self-test arm: "an empty population is NOT a pass", exit 2). A permanently refusing gate reports
# nothing and teaches the team to ignore it. Listing the findings keeps the gate live: a NEW in-place
# change, to a create script, after this reset, is not in this set and still fails.
#
# DELETE THIS WHOLE BLOCK AT 10.0.0-rc.1. The schema freezes there, the migration chain becomes
# append-only, and from that point an in-place create-script change genuinely is the defect this gate
# was written to catch. Every line below is then stale, which this gate already fails on -- so the
# block removes itself by the rule that governs the rest of this file.
# ---------------------------------------------------------------------------------------------

#
# THE DESTROYED-KEYS LEDGER TABLE, both dialects. Its CREATE TABLE in 001 was edited in place when the
# key-destruction ledger landed and again when its primary key became the pair (handle, generation), so
# this checker is right that the create script changed and right to ask how an existing database follows.
#
# IT CAN FOLLOW, and the reason the checker cannot see it is worth stating rather than leaving a bare
# baseline row: the upgrade path is a DROP AND RECREATE in the ledger migration script, not a sequence of
# ALTERs. The checker matches a delta against ALTERs naming the same column, so a migration that replaces
# the whole table matches nothing and every column reads as unmigrated.
#
# The recreate is deliberate. Rows written by the earliest shape record a destruction by (request, handle)
# and carry NO generation, and a generation cannot be back-filled -- the value only ever existed inside
# the key backend and the destruction annihilated it. A row with no generation cannot answer the read
# predicate, so keeping it would force the predicate back onto the handle, which is the defect the pair
# exists to remove. The migration's guard tests the FINAL shape rather than an earlier one, so a database
# at either earlier shape is migrated and one already migrated is skipped; both scripts disclose the
# destructive consequence in their own headers, including that an erasure mid-retry must be re-filed.
#
# WHAT THIS BASELINE COSTS: nothing now checks mechanically that the recreate stays equivalent to the
# create script. If 001 gains a column and the migration does not, these rows keep this gate quiet. A
# checker that recognised drop-and-recreate as an upgrade path would close it. Tracked in the issue
# tracker against this file; no identifier is written here because eng/** is copied to the public mirror.
