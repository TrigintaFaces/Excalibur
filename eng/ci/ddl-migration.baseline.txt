# ddl-migration-completeness baseline.
#
# Each non-comment line records something the gate found and we have not yet closed, so that CI is
# green on the tree as it stands and only a NEW gap fails. A baseline is a record of known debt, not
# a place debt goes to be forgotten -- so it is enforced as a SET, in BOTH directions:
#
#   * an entry that is no longer produced is STALE and FAILS the gate. When the missing migration is
#     written, or a verification learns to read columns, the finding disappears and the line here
#     must be deleted in the same change. A forgiveness list that only ever grows stops recording
#     anything.
#   * a finding that is not listed here FAILS the gate. That is the point.
#
# The anchor bounds the committed history the gate walks. It is a commit, never a count: a rolling
# N-commit window would silently drop an entry out of scope, at which point the line here would read
# as stale and be deleted while the defect was still shipping.
#

#

# src/Dispatch/Excalibur.Dispatch/ErrorHandling/PoisonMessage/schema.sql no longer contains schema.
# Excalibur.Dispatch is the messaging core and holds no SQL dead-letter store, so it was shipping
# DDL for tables owned and written by other packages. The SQL Server definition moved UNCHANGED to
# Excalibur.Data.SqlServer/Scripts/001_CreateDeadLetterSchema.sql, column for column, including both
# TenantId upgrade arms -- the additive ADD COLUMN for a database created before the column existed,
# and the collation rewrite for one created before Latin1_General_BIN2 was pinned.
#
# So there is no column change for a consumer to follow: TenantId was not altered, dropped or
# retyped, and the migration an upgrading consumer needs is present and guarded in the replacement
# script, which is a no-op on a database that already has it. The finding is an artifact of where
# the text lives, not of what the schema says.
#

# empty of schema; it forgives nothing about the table itself.

# The three erasure-certificate columns below are a KNOWN gap with a filed decision, not an accepted
# shape. The shipped 001 declares all three, so a FRESH install is correct; a database provisioned
# before they were added has the table without them and re-running 001 does not repair it.
#
# They are recorded here rather than migrated because the backfill is a compliance decision and not
# a schema edit. There is no payload blob to recover the values from -- these columns ARE the
# certificate -- and the row carries a Signature computed over the OLD field set, so populating them
# with any value yields a signed artifact whose content nobody signed. Exceptions in particular is
# the Article 17(3) record of data lawfully RETAINED: defaulting it to an empty array would assert
# to a regulator that an erasure had no lawful-retention exceptions, when the truth is that none
# were recorded. The package's own ARCHITECTURE.md already refuses that conflation one field over --
# "false means NOT ESTABLISHED, for any reason" -- and the migration has to extend the same
# distinction here. Tracked: Excalibur_Dispatch-ovpiky (ProductManager owns the semantics).
#
# This baseline is a SET in both directions: when that migration lands these three lines must be
# deleted in the same change, or the gate fails them as stale.
Excalibur.Compliance.SqlServer:ErasureCertificates:EXCEPTIONS
Excalibur.Compliance.SqlServer:ErasureCertificates:GENERATEDAT
Excalibur.Compliance.SqlServer:ErasureCertificates:VERSION
