## What didn't work

**Eight measurements of one population, across five people.** `12 → 13 → 14 → 7 → 8 → 16 → 15 → 9` — count them; the heading of an earlier draft of this very section said *seven*, which is the defect this section is about, committed inside the report describing it. Every one was a correctly-executed query. Every one was scoped to a different population, and **no one stated the population alongside the number.**

```
"has a .sql, how is it shipped?"   missed packages shipping none
"named *.SqlServer|Postgres|Oracle" missed EventSourcing.Sqlite entirely
"writes && ships no .sql"           counted self-provisioning stores as broken
```

Each proxy was the best available until the next exposed it. **The cost was roughly two hours of the sprint's most senior attention spent re-deriving a number that was never the deliverable.**

**A 20-minute infrastructure outage degraded 30% of the roster for the remaining three hours.** Two poll hooks exited on unreachability and never restarted; one session hung. The hooks failed *correctly and loudly* — and nothing was listening. Restarting the OPCOM container revived only sessions whose hooks were still running.

**A ruling was applied to one artifact and treated as done.** The sprint retitle reached the plan and not the mission record, which still asserts a completion the sprint explicitly cannot certify. No rename tool exists, so it required a channel warning and two separate broadcasts to keep it out of the changelog.

**The tracker export lagged twice**, each time leaving a closed bead reading `open` (or absent) in committed HEAD — the state a returning agent reads.

## Surprises

- **A shipped sample taught permanent data loss and no gate could see it.** Awaiting a `Task<long>` and discarding the result is legal C#. No build gate, analyzer, or test could detect it. Found only because SAMPLES read the code against the contract.
- **A build break wore a test-failure exit code.** An orphaned test host survived killing the `dotnet`/`vstest` chain, kept holding test DLLs, and made the *next* shard die `MSB3021` — producing `EXIT=1` with zero failing tests.
- **A shard reported green while its headline assembly never ran.** `EXIT=127`, and the one `Passed!` line belonged to a sibling assembly one path-segment away.
- **The sprint title was the only artifact nobody thought to verify** — and it has the widest reach of anything produced.

## Recommendations

**1. [CONTINUE] Re-verify claims handed to you, even from someone who verified them.**
*Evidence:* every material defect this sprint was caught by a second person re-measuring, not by the original author. Cost is minutes; the alternative is a false claim propagating into a durable artifact.

**2. [CHANGE] State the population with every count, or publish a predicate instead of a number.**
*Evidence:* eight counts of one population, none wrong, all differently scoped. `fuju06`/`flxbou` finally closed as a re-runnable predicate — that should have been the first move, not the eighth.
*Effort:* zero. It is a sentence next to the number.

**3. [STOP] Treating a ruling as applied when one artifact carries it.**
*Evidence:* the retitle reached the plan, not the mission record; a P1 bead was filed on a premise that had already been narrowed. *Impact:* a claim ruled out hours earlier cannot resurface in the changelog.

**4. [TRY] Make phase dispatch refuse an unreachable target.**
*Hypothesis:* a phase that cannot start should fail loudly rather than report `active`. Two phases dispatched into dead sessions this sprint and were caught only by comparing poll-log mtimes by hand.
*Measurement:* `jdzbbc` — a dispatch to an agent whose hook is stale beyond a bound reports unreachable, not active.

**5. [TRY] Ask the progress question before the liveness question.**
*Hypothesis:* "has the artifact appeared?" is cheaper and more reliable than any liveness telemetry. Three times this sprint, `whois status`, heartbeat age, and the `REWAKE`-without-`START` discriminator **all** pointed at "hung" for an agent who was mid-build. The file mtime settled it every time.


Per `rule-promotion-gate`, the default is **no new rule**, and neither candidate clears the bar. Writing
either would duplicate an existing clause and tax every future session for nothing.

**The uncomfortable part is what that implies.** Eight scope errors happened tonight across five agents
while `verify-before-claiming:337` already said exactly the right thing, and three liveness
false-positives happened while `CLAUSE 0` already said exactly the right thing. **Every agent involved
had both rules loaded.** The corpus was correct and did not fire.

`rule-promotion-gate` §6 anticipates this: *a rule is a teaching artifact; it does not fire. Prose has
no `exit 1`.* The honest response to a recurrence under an existing rule is **a mechanism, not another
paragraph**:

- the shipped-DDL population is now a **re-runnable predicate** on `fuju06`/`flxbou`, with a ~25-line
  detector carrying its own controls in both directions — that is the gate the eight counts should have
  been
- `jdzbbc` makes dispatch refuse an unreachable target instead of reporting `active`
- `d0fqyz` makes a poll hook survive transient unreachability

**Adding a ninth rule about scope would have been the easy move and the wrong one.**
